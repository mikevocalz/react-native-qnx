# Agent execution contract: react-native-qnx

This is a Fabric-only, Hermes-first out-of-tree React Native platform. QNX is an existing target; MarathonOS is a proposed additional Linux/Wayland target. **Do not replace the renderer.** The reusable components are `rnqnx_views_qt`, `rnqnx_fabric_adapter`, `rnqnx_react_host`, the JavaScript platform overrides and the Metro/Expo/Nitro toolchain.

## Startup sequence (mandatory)

1. Read `README.md`, `docs/handoff/CURRENT_STATE.md`, `docs/component-support.md`, `docs/marathon/ARCHITECTURE.md`, `docs/marathon/ROSTER.md`, `docs/marathon/SKILLS.md` and the relevant ADRs completely.
2. Inspect current base, existing PRs, exact npm tags, Expo SDK compatibility, upstream Marathon manifests and source interfaces. Never rely on memory for changing APIs.
3. Select roles from the roster by workstream, attach concrete path ownership and deliverable/acceptance evidence.
4. Install and **read** exact relevant skill SKILL.md files. For Nitro and native APIs, use Margelo `api-design` → `build-nitro-modules` → `cpp` first; add `nitro-fetch`, `react-native-mmkv`, `swift` or `kotlin` only when the API actually needs them. Record upstream commit SHA, selected version, and what decision the skill changed. No skill invocation may be claimed without proof.
5. Make one small vertical slice at a time; expose an opt-in CMake or Metro feature flag until a device run proves it.
6. Run the repository's dependency, typecheck, Metro bundle, host native/ASan, CMake and runtime gates. Separate host-only, Linux/Wayland, emulator, QNX VM and physical hardware evidence.
7. Document measured results, missing tests, known incompatibilities, upstream collaboration needs, and rollback in each PR. Leave PR in draft if the runtime/target result is missing.

## Engineering invariants

- Preserve QNX target, existing QNX Screen probe, RN/Qt Quick renderer and QNX SDP toolchain.
- Never claim that a successful host-renderer test proves a QNX/Marathon device run.
- Distinguish operating system (QNX vs Linux), display backend (Screen vs Wayland), and JavaScript platform identity (qnx vs marathon).
- Use Qt Quick as React Native's existing Fabric component backend. Do not introduce Flutter, WebView, Qt Widgets, Android emulation, egui or a second renderer.
- Reuse Hermes, Yoga, Fabric, JSI, Nitro and Expo modules where the audited release supports it. Do not bypass permission or app isolation boundaries for feature parity.
- MarathonOS permissions and sandbox constraints are first-class requirements: no assumed shell singleton access, root access, direct unrestricted D-Bus, or implicit network permission.
- New CMake switches must default OFF and reject unsupported hosts. Bundler aliases must never change an existing QNX bundle.
- Native modules must have explicit ABI/toolchain compatibility and a tested failure path.
- Do not use release candidates or pre-release ABI changes silently. Nitro 1.x alpha and Expo Modules API 2.0 beta require explicit migration experiments.
- Match upstream npm releases with exact version pins and a regenerated locked dependency graph. Do not merge package.json-only upgrades.
- No unreviewed autogenerated source, no fake test or benchmark numbers, and no claims of publication/official Marathon support before upstream acceptance.

## Required PR report

Every PR: architecture boundary, source inspection, changed files, skill/version/decision table, test commands and actual logs, QNX regression check, Marathon-specific check, security/licensing impact, performance budget, limitations, reviewers, next PR, and rollback instructions.
