## What the device paths wait on

The Pi apps do not expose their object tree. The Screen probe has no Qt tree at
all, and the Qt apps print window events, not node names. So the device scripts
wait on **named lines the app prints**, not on `objectName`s:

- `install-pi.sh`: `rnqnx_playground: first frame presented`, 30 s by default
  (`RNQNX_PI_FRAME_WAIT_S`, 1 to 300). On timeout it kills the probe, exits 31
  and names the line.
- `pi-mouse-smoke.sh`: a new `RNQNX_WINDOW_FRAME` line after each drag, a new
  `RNQNX_WINDOW_ACTION` line after each double click, 10 s by default
  (`RNQNX_MOUSE_WAIT_S`).

`rnqnx_wait_node` waits for `RNQNX_NODE name=<objectName>`, the line a tree
beacon would print. No app prints it yet. Wiring a beacon into the consumer app
main is in `native/window-chrome` and `vnext/src/runtime`, which other lanes own,
so it is a follow-up for S5 or S9. The host Qt path does wait on real nodes.

`rnqnx_wait_log` checks the log once per `RNQNX_WAIT_POLL_S` seconds (default 1)
and counts checks to bound the wait, so it does not need `date +%s`. The
interval spaces the checks. A missing line fails the wait; nothing is assumed.

One semantic loss: the old double-click check slept 1.5 s and then asserted
exactly one new `RNQNX_WINDOW_ACTION`, which also caught a late second action.
The new check waits for the first and then asserts exactly one at that moment.
