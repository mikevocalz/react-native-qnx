# Marathon VM run, 2026-11-20

`rnqnx_marathon_host` ran as a Wayland client of the real Marathon-Shell compositor in a Linux VM. The host was built on Alpine/musl. This is a VM on a Mac, with software rendering and no GPU. It is not a MarathonOS device run, and it says nothing about performance.

## Setup

| Item                   | Value                                                                                                                                                                                                                                                           |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| VM                     | Lima 2.3.0, `vmType: vz`, Alpine 3.24.4 aarch64, kernel 6.18.60-0-virt, 4 CPUs, 6 GiB, 40 GiB sparse disk                                                                                                                                                       |
| Compositor             | `marathon-shell-bin`, `MARATHON_VERSION` 1.0.0, upstream `patrickjquinn/Marathon-Shell` at `1f845160f0c249cb29da127fb66abaad380b5438`, built from source, no local patch ([marathon-shell-local-patches.diff](logs/marathon-shell-local-patches.diff) is empty) |
| Compositor display     | `WAYLAND_DISPLAY=marathon-wayland-0`, `XDG_RUNTIME_DIR=/tmp/xdg`, `DBUS_SESSION_BUS_ADDRESS=unix:path=/tmp/xdg/bus` ([compositor-env.txt](compositor-env.txt))                                                                                                  |
| Qt                     | 6.11.1 from Alpine (`qmake6 -v`), the version the repository pins. Alpine's `qt6-qtbase`, `qt6-qtdeclarative`, `qt6-qtwayland`                                                                                                                                  |
| Host                   | `rnqnx_marathon_host`, Debug, clang 22.1.3, ELF aarch64 with interpreter `/lib/ld-musl-aarch64.so.1`. `ldd` and `file` output: [environment.txt](environment.txt)                                                                                               |
| Node for the JS bundle | 26.13.1 (the version `marathon-qt-host.yml` pins). Alpine ships 24.22.3, which was not tried                                                                                                                                                                    |
| Rendering              | Shell on Qt's `vnc` QPA (and `offscreen` for the first run) with `QT_QUICK_BACKEND=software`. The VM has no `/dev/dri`, so the shell advertises no dmabuf or `wl_drm`                                                                                           |

"Marathon's Qt" is Alpine's Qt 6.11.1. The Marathon image build uses Alpine containers (`docs/BUILDING.md` section 0 in the shell repository), and Alpine 3.24 ships the pinned Qt. The Qt version inside an actual Marathon image was not checked.

Input reached the shell through Qt's `vnc` platform plugin and a small RFB client ([scripts/rfb.py](scripts/rfb.py)): the shell's window has no other injection route in a VM (no `/dev/uinput`, and the shell serves no virtual-keyboard or virtual-pointer global). The shell's own SIGUSR1 handler wrote the shell screenshots; the RFB client captured the others.

The Back run used `MARATHON_NATIVE_BACK_MS=4000`. With the default 350 ms the shell judged the first Back unhandled and went home, because React rendered and Qt committed the repaint slower than that in this software-rendered VM. That timing is a property of this VM, not a measurement of a device.

## What did not run

| Item                                                           | Why                                                                                                                                                                                                                                                                              |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Touch events                                                   | No `/dev/uinput`, and Qt's `vnc` plugin sends pointer events. The shell converts touch to `wl_pointer` events for native clients (`shell/src/wayland/nativesurfaceitem.cpp:50-62`), so a touch would reach the host as the pointer path above. A physical touch was not produced |
| Mouse wheel                                                    | RFB wheel events through the `vnc` plugin produced no `wl_pointer.axis` at the client. A second run on Qt's `xcb` plugin with `xdotool` did deliver `wl_pointer.axis` to the client, and the host logged no scroll. The cause is not found                                       |
| Shell back gesture (pill swipe)                                | Neither RFB drags nor `xdotool` drags on the navigation bar triggered `swipeBack`. Back was driven with the Escape key, which the shell's key routing turns into the same back request (`shell/src/wayland/keyrouting.h:33-37`)                                                  |
| On-screen keyboard and `zwp_text_input` enable and commit      | Keys arrived as key events through the shell's own window. Whether focusing the field made the client send a text-input enable was not checked, no keyboard panel appears in the screenshots, and no commit through `text_input_v2` or `v3` was exercised                        |
| Keyboard inset or resize on keyboard open                      | Not observed. The shell sends `ime_inset` 0 and the source suggests the configure size does not shrink (see `contracts.md` section e). It needs a client with text-input focus and a keyboard panel                                                                              |
| cgroup freeze, runner pool, sandboxed apps                     | The VM has no delegated cgroup and the shell reported the runner pool off (`bwrap` cannot find `/usr/share/marathon-apps`)                                                                                                                                                       |
| Hardware, HackberryPi CM5, a phone, GPU rendering, performance | Not available                                                                                                                                                                                                                                                                    |
| `grim`, `wtype`, `wlrctl`                                      | Installed, and unusable: the shell advertises no screencopy, virtual-keyboard or virtual-pointer global. `grim` fails with "compositor doesn't support the screen capture protocol"                                                                                              |

## Defects found by running it

| Finding                                                                                                                                                                                                                                 | Root cause                                                                                                                                                                                                                                                             | Fix                                                                                                                                                                                                                         |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Host aborts about 8 s after launch with `Assertion failed: bounds == detail::thread_stack_bounds_impl()` and, with that check off, fails every JS call from the event loop with `Maximum call stack size exceeded (native stack depth)` | musl's `pthread_getattr_np` reports the main thread's stack as the part mapped so far (135168 bytes at start, 4153344 after touching 4 MB; `scripts/musl-main-stack.c`), glibc reports `RLIMIT_STACK`. Hermes caches the first answer and treats it as the whole stack | `native/platform/linux-host/MainThreadStack.hpp` touches the stack down to the limit before Hermes starts. `rnqnx_marathon_main_stack_test` fails without it (1052672 < 90 percent of 8388608) and passes with it (7868416) |
| Pressable never fired in the Marathon host                                                                                                                                                                                              | Touch and mouse dispatch to JS is behind `RNQNX_ENABLE_INPUT_LIFECYCLE`, default OFF, and the Marathon host build did not turn it on                                                                                                                                   | The CI recipe and the build commands in `NATIVE_HOST.md` pass `-DRNQNX_ENABLE_INPUT_LIFECYCLE=ON`                                                                                                                           |
| React Native 0.88 headers fail to compile with libstdc++ 15                                                                                                                                                                             | `core/ReactPrimitives.h` and `jsinspector-modern/ExecutionContext.h` use `int32_t` and `int64_t` without `<cstdint>`                                                                                                                                                   | `-include cstdint` for upstream RN targets in `cmake/dependencies/ReactNativeRenderer.cmake`                                                                                                                                |
| Hermes `llvh` fails to compile on musl                                                                                                                                                                                                  | The `lseek64` probe succeeds, but musl declares `lseek64` only under `_LARGEFILE64_SOURCE`                                                                                                                                                                             | `HAVE_LSEEK64` off on LP64 Linux in `cmake/dependencies/Hermes.cmake`                                                                                                                                                       |
| `check-wayland-client-log.py` found nothing                                                                                                                                                                                             | libwayland 1.24 and later print `xdg_toplevel#16` where earlier versions printed `@16`                                                                                                                                                                                 | The regexes accept `[@#]`                                                                                                                                                                                                   |

One item is left open: the Debug host is built with AddressSanitizer, and at exit it reports a 96-byte LeakSanitizer leak (`logs/probe-host.err`, bottom of `logs/direct-wayland-client.log`), so a run that exits on its own ends with status 1. The allocation happens during Wayland registry binding inside `libwayland-client` and `libQt6WaylandClient`. The frames are unsymbolized and none are in repository code. The results above are not affected by it.

## Files

- `SHA256SUMS`: hashes of every other file in this directory.
- `contracts.md`: what Marathon-Shell exposes to a client, with `file:line` citations into the shell source.
- `environment.txt`, `compositor-env.txt`: versions, `ldd`, `file`, hashes, how the compositor was started.
- `logs/`: compositor logs, build logs, wayland-info, host stdout and stderr, step log.
- `screenshots/`: shell home screen, the host in front of the shell for each step.
- `scripts/`: the exact scripts used (`start-marathon-vnc.sh`, `run-probe-all.sh`, `run-direct.sh`, `rfb.py`, the `.desktop` entry).
- `baseline-first-binary/`: the first host binary, before the stack fix, against the offscreen platform and headless Weston 14.0.2. Kept for comparison.
