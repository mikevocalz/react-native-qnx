## Neutrino concepts that must remain explicit

- **Message passing, multipart messages, pulses, client/server and RPC:** Plan 07 owns framing, bounded memory/admission, `rcvid_t`, correct SEND/REPLY blocking, registered events, cancellation and reply ownership. Plan 08 owns reconnection and unknown mutation outcomes.
- **Message queues and pipes:** Plan 14 compares applicable supported IPC mechanisms for the real workload. They are not automatically replacements for the chosen transport or extra hops in the Fabric pipeline.
- **Atomic operations, mutexes, condition variables, semaphores, threads and TLS:** Plans 01/14 own deterministic readiness, RAII lifetime, supported synchronization and measured contention. A sleep is not a readiness protocol. Shared-process and shared-thread synchronization require different contracts.
- **Clock, nanosleep, alarms, interval timers and TimerTimeout:** Plans 03/07/14 use monotonic deadlines, account for queue time, verify timeout blocking states and use current supported APIs. Wall-clock changes must not corrupt elapsed measurements. The archive's receive-timeout example is not a client-RPC deadline implementation.
- **Signals, scheduler, starvation and SMP:** Plans 01/08/14 keep signal handling safe, supervision independent of a stalled JS loop, and priority/affinity changes evidence-driven. QNX does not make Hermes GC or React rendering hard-real-time.
- **Shared memory and allocators:** Plan 09 requires a measured use case, generation-scoped leases, bounded backpressure and safe mapping lifetime. A raw address is not a cross-process resource handle.
- **Interrupt examples:** Plan 14 reviews QNX 8's changed interrupt APIs and thread model. An app module must use an authorized service/driver; no JS interrupt handler, hard-coded legacy IRQ or gratuitous privilege is proposed.
- **Resource-manager examples:** Plans 07/14 verify credential checks, message sizes, offsets, actual transferred counts, OCB/lifetime and the framework's synchronization behavior. Do not infer a data race from globals without inspecting framework locking.

## Current official documentation and examples

Published Plan15 records the broader official QNX source audit and separates inspected sections, discovered indexes and pending target gates. Published Plan14 specifies proposed fresh QNX8 native probes; the feature plans own production integration. Current documentation is checked against the installed SDK/image/BSP rather than used as permission to upgrade them silently.

Every application-facing native interface follows [Nitro v1 API-first design](NITRO_V1_API_POLICY.md). Internal C/C++ system probes may test OS contracts directly; they do not become raw syscall/command APIs exposed to JavaScript. Root/native privileges and OS-specific details remain behind the actual service boundary.

No archived source, binary, generated Photon code, proprietary documentation or SDK library is vendored by these plans. An example is accepted as evidence only after a supported current implementation, bounded negative tests and a separately labeled target run. Reverting this map changes no platform behavior.

## Readiness source checks — 2026-11-07

The GitHub tree API verified the supplied commit's `QNX Neutrino RTOS/Programming`
path resolves to the recorded tree. Its untruncated recursive inventory contains

not all file bodies, historical PDF contents or implementation correctness.

Three official pages were inspected for the current constraints below:

- [MsgSend](https://www.qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.lib_ref/topic/m/msgsend.html): a caller can wait in SEND or REPLY states. A JS Promise alone does not move that blocking native operation off its owner thread.
- [TimerTimeout](https://www.qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.lib_ref/topic/t/timertimeout.html): select the applicable SEND/REPLY timeout states immediately before the intended kernel call. An intervening kernel call can clear the timeout; a server using the unblock channel policy must cooperate in releasing a received request. Caller timeout does not establish cancellation of a server-side business effect.
- [QNX8 kernel migration](https://www.qnx.com/developers/docs/8.0/com.qnx.doc.qnxsdp.migration/topic/kernel.html): receive IDs use64-bit `rcvid_t`; saved32-bit IDs can break later comparisons. Current runmask rules also require a matching configured cluster.

These are bounded source checks, not an exhaustive current-manual/example audit,
a selected transport implementation or a target execution result. Broader source qualification and all system probes remain implementation work;
publishing Plans14/15 does not execute those gates.
