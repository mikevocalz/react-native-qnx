## Behavior and scope

`RnsvgRootItem::geometryChange` previously called `update()` on the item whose
geometry changed. A nested root is hidden and drawn into the outer root's
texture, so resizing that nested item did not invalidate the visible texture.
For an outer root, repainting alone did not schedule the layout pass that
places live `ForeignObject` children and refreshes cached `onSvgLayout` bounds.

Geometry changes now use the existing `invalidate()` path. It schedules both
painting and polish on the outermost SVG root. The two regressions run a real
offscreen Qt Quick window and change retained item sizes without reapplying
props or calling `render()` or `layoutScene()` manually:

- A nested SVG grows from 40 to 80 pixels, then shrinks to 20 pixels. Each
  change must schedule an outer layout and paint, and change the sampled
  visible pixels.
- An outer SVG grows from 100 to 200 pixels with the same 100-unit viewBox.
  Its embedded view placement and cached element bounds must scale together.

This is evidence for layout-only retained-item mutations. The current Fabric
update path also reapplies component props, which can mask the missing
geometry invalidation; this receipt does not claim a reproduced public React
update failure. The fix adds no API, dependency, thread, or renderer backend.
Fabric, Hermes and Qt Quick remain in place, and SVG remains default OFF.

The SVG guide also corrects an obsolete limitation. The existing
`build-svg-qnx.sh` builds the optional QtSvg library and `qsvg` image plugin,
and transactional staging includes them when their build artifacts are
present. The [November 13 device receipt](pr161-device-gallery-2026-11-13.md)
already records SVG image sources rendering with those artifacts. That
historical evidence does not qualify this continuation. The guide still
records the separate uncached-image completion limitation.
