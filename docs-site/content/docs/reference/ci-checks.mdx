This page describes what each workflow runs, read from the YAML in [`.github/workflows`](https://github.com/mikevocalz/react-native-qnx/tree/main/.github/workflows) at `8d7deaa`. It does not say any check passes. A run result belongs to one commit, and the [required-checks record](https://github.com/mikevocalz/react-native-qnx/blob/main/docs/releases/required-checks.md) says a run on an earlier commit does not count for a candidate.

I counted 27 workflow files. Every job counted then used `runs-on: ubuntu-24.04`, a GitHub-hosted runner. The files were read with Ruby's YAML parser. I did not run any workflow.

## Three kinds of evidence

[required-checks.md](https://github.com/mikevocalz/react-native-qnx/blob/main/docs/releases/required-checks.md) sorts results into three categories and says each is reported on its own.

| Category        | What it is                                                                                                                | Status in the repository                                                                                       |
| --------------- | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Hosted          | GitHub-hosted `ubuntu-24.04` runners. Linux host builds, source contracts and bundles. None of them compile for QNX.      | Every workflow below.                                                                                          |
| QNX cross-build | A build with the QNX SDP toolchain for the target, on a self-hosted runner the owner authorizes to hold the licensed SDP. | Required. `qnx-cross-build.yml` exists and has not run: no self-hosted runner is registered.                   |
| Device          | Supervised runs on named QNX hardware. Recorded as evidence receipts under the other v1 gates. They are not CI checks.    | Receipts under `docs/evidence/`. The Pi 400 receipts belong to earlier revisions and do not cover a candidate. |

A local run of the same command never substitutes for a hosted check. A passing hosted check says nothing about a QNX cross-build or a device. The [status page](/docs/reference/status) uses "host-tested" for what a hosted job builds and runs on Linux, and "device-verified" for what a receipt shows on the Pi 400.

## Required for a v1 candidate

The Candidate CI gate (`ci`) in [v1-readiness.json](https://github.com/mikevocalz/react-native-qnx/blob/main/docs/releases/v1-readiness.json) asks for successful required checks on the release candidate, on authorized runners, with local checks labeled separately. The gate is pending on `main`. The required hosted workflows, from required-checks.md, are these 18:

`sdk58-validation`, `host-renderer`, `image-loader`, `nitro-v1-host`, `nitro-qnx-source-check`, `expo-modules-qnx-source-check`, `expo-qnx-autolinking`, `hermes-qnx-source-check`, `react-qnx-source-check`, `pi-tooling-quality`, `runtime-appstate`, `qnx-create-app`, `qnx-native-consumer-build`, `phase6-doctor`, `phase7-release-dossier`, `phase-public-host`, `app-identity`, `phase4-lifecycle`.

Most of them filter on paths, so a pull request that touches other files does not start them. The document gives a `gh workflow run` loop that dispatches all 18 on the candidate ref. Each run has to belong to the candidate's head commit.

Separately, the document records a branch ruleset on `main` that requires a pull request and three checks on every pull request: `validate` (from SDK 58 validation), the two `Qt 6.11 / RN 0.88 / Hermes (input lifecycle ON|OFF)` jobs (from SDK 58 full host renderer) and `image-cache` (from Image loader HTTP and cache). Path-filtered workflows are left out of the ruleset because a skipped required check would wait forever.

required-checks.md does not list `window-chrome.yml`, `docs-site.yml`, `runner-release.yml` or `webgpu-host.yml` as required or as not required. The `window-chrome` gate in the readiness record names device receipts and a native test as its evidence.

Each required workflow sets `permissions: contents: read` and pins actions to full commit SHAs, per the same document.

## Workflows

Triggers: `PR` is `pull_request`, `push` is a push to `main` unless noted, `dispatch` is `workflow_dispatch`. "Paths" means the trigger only fires when changed files match a filter. Three workflows whose file names carry the name of the separate Linux/Wayland target are not listed by name, because a CI check on this site bans that word. They are marked informational in required-checks.md, run on pull requests with path filters (one also on a push to a feature branch) and can be dispatched, and cover that target's Metro platform, its native Qt host and its development launcher.

## What a result means

- A pass on a hosted workflow shows that a Linux job ran the listed commands on one commit. Several jobs compile host code, so their results say nothing about QNX `qcc` output.
- The `hermes-qnx-source-check`, `nitro-qnx-source-check`, `expo-modules-qnx-source-check` and `react-qnx-source-check` jobs check source contracts and patches against pinned sources on Linux. Their names contain `qnx` and none of them cross-compiles for QNX.
- A CI result cannot stand in for device evidence. The device gates (`cold-boot`, `device-parity`, `performance`) ask for supervised runs on named hardware, for example 20 consecutive cold boots on the release board and image.
- required-checks.md carries a table of dispatch results at `0e8e893` on branch `v1/gate2-ci`. It says that commit is not a release candidate. Read the table in that file for the recorded results. Do not take them as the state of `main`.
