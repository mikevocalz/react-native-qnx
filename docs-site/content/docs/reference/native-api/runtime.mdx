```cpp
class QnxDevSupport final : public QObject
```

Doc comment:

```text
The development client: loads the bundle from Metro instead of the staged
bytecode, implements the native half of Fast Refresh (DevSettings,
DevLoadingView, LogBox), keeps Metro's /message connection for `r`/`d`
from the terminal, and draws the native loading banner, error screen and
developer menu. Only built with RNQNX_ENABLE_DEV_SUPPORT; a release build has
none of this code.

Lifetime: one per window, created before the first React host and kept
across reloads. Each reload creates a new QtReactHost; this object only
signals and never touches a host itself.
```

### `rnqnx::runtime::QtReactHost`

Kind: class · Namespace: `rnqnx::runtime` · Source: [vnext/include/react-native-qnx/runtime/QtReactHost.h#L195](https://github.com/mikevocalz/react-native-qnx/blob/main/vnext/include/react-native-qnx/runtime/QtReactHost.h#L195)

```cpp
class QtReactHost
```

Doc comment:

```text
Owns a Hermes runtime and the React Native scheduler wired to Qt Quick.

This is the layer React Native has no generic implementation of: the package
ships `react/runtime/platform/ios` and nothing else, so the host wiring is
ours. By default JavaScript runs on the thread that constructs this object.
With `Options::jsThread` it runs on a thread this object owns, and the
constructing thread stays the GUI thread (ADR-0021).

In JS-thread mode the public calls fall into three groups.
- Awaited: they run on the JS thread and the caller waits, then mounts they
  caused are applied before the call returns. Those are `evaluate`,
  `startSurface`, `stopSurface`, `commit`, the `install*` calls,
  `registerTurboModule`, `addTeardownHook`, `setTurboModuleProvider`,
  `lastError`, `javaScriptErrors` and `hasFabricUIManager`.
  They block the GUI thread for as long as JavaScript is busy, so start-up
  and teardown code may use them and input handlers must not.
- Posted: `resizeSurface`, `setWindowSize` and `callFunctionOnModule` queue
  the work and return.
- Thread-bound: `runtime()` returns a reference only the JS thread may use;
  it terminates the process when called from another thread. Use
  `runOnJsThread`. `scheduler()` and `delegate()` hand out references to
  objects the JS thread uses; call only their GUI-owned members from the
  GUI thread (`delegate().setTouchDispatcher`, `lastFailures`,
  `mountedTransactionCount`).
- Rejected: `setOwnerPoster` throws, because the host installs the poster
  that moves mounts to the GUI thread.

A module that needs the GUI thread (AppState) refuses to load in this mode,
and `registerTurboModule` factories and teardown hooks run on the JS thread
and must not wait on the GUI thread: the destructor holds it.
```

```cpp
class QueuedCallTarget : public QObject
```

Doc comment:

```text
A receiver for work posted from another thread, run by the receiver's event
loop in post order.

This replaces `QMetaObject::invokeMethod(..., Qt::QueuedConnection)` for the
host's thread hand-offs. The behaviour is the same, with one difference that
matters for testing: the work is carried in a `QEvent` this code allocates,
so the release before `postCall` and the acquire in `event()` cover every
byte of it. `invokeMethod` copies its callable inside Qt's queue, where
ThreadSanitizer cannot see an ordering edge, so every such call is reported
as a race on the callable. The annotations compile to nothing outside a
ThreadSanitizer build.

Destroying the target drops work it has not run yet.
```
