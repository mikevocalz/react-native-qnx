---
title: Animation runtime
description: How Worklets, Reanimated 4 and Gesture Handler 3 run on the Qt host, which thread owns each step, and what the Pi 400 runs showed about frames, springs and gestures.
---

Animation libraries on this platform run in three layers. `react-native-worklets` 0.13.1 supplies a second JavaScript runtime on its own thread. `react-native-reanimated` 4.7.1 builds shared values and animated styles on that runtime. `react-native-gesture-handler` 3.4.0 supplies the gesture JavaScript, while the recognizers themselves are C++ written for this host. Upstream JavaScript runs unmodified. All three switches (`RNQNX_ENABLE_WORKLETS`, `RNQNX_ENABLE_REANIMATED`, `RNQNX_ENABLE_GESTURE_HANDLER`) default to OFF, and each CMake step rejects a version outside its supported range.

This page covers the threads, the seams between them and the evidence. Sources: `docs/worklets-qnx.md`, `docs/reanimated-gesture-handler-qnx.md`, `docs/adr/0020-worklets-reanimated-gesture-handler-bootstrap.md` and the receipts under `docs/evidence/`.

The Qt GUI thread runs React, Hermes, module calls and Qt item changes. By default the host has no separate JS thread (an opt-in one exists, ADR-0021, and does not run worklets yet), so the UI-worklet thread (`rnqnx-ui-worklet`) is a third thread added beside the render thread, and not a replacement for the JS thread. On the Pi 400, the app logged `[gui]` for the JS thread role and `ui-worklet` for the worklet role in every run.

## The seams

**JS to UI.** `QtUiThread::post` queues one call per batch, scheduled by `QtUIScheduler` (`vnext/src/worklets/`).

**UI to JS.** `QtTaskQueueCallInvoker` posts to `QtRuntimeTaskQueue`. React Native's own call invoker cannot serve here. This host's runtime executor runs a callback inline on the caller, which would execute JavaScript on the UI-worklet thread.

**Frames.** `QtFrameBridge` (`vnext/src/worklets/QtFrameBridge.cpp`) connects to `QQuickWindow::afterAnimating`. A frame request marks the window dirty once per outstanding batch. When the signal fires on the GUI thread, the bridge swaps the pending callbacks into a batch and runs them on the UI thread with a `steady_clock` millisecond timestamp. No timer is involved. A hidden or unexposed window produces no frames, and so no callbacks. The bridge follows one window.

**Mounting.** Qt items change only on the GUI thread. Reanimated commits from the UI thread, so `QtSchedulerDelegate`'s owner poster re-posts the mount. The delegate also reports a successful mount to the `UIManager` through `setMountReporter`. This hook came out of a device finding. On the Pi, a shared value advanced to 222.133 while pixels stayed put until a React commit, because the scheduler never called `reportMount`, and the pinned Reanimated mount hook resumes paused animation commits there. The fix and its host test are in `docs/validation/pr149-frame-mount-2026-11-13.md`. Failed mutation batches are not acknowledged.

## How the libraries attach

Each library looks up a named TurboModule and expects the native side to install a global proxy: `WorkletsModule` (`__workletsModuleProxy`), `ReanimatedModule` (`__reanimatedModuleProxy`) and `RNGestureHandlerModule`. ADR-0020 registers those three through `QtReactHost::registerTurboModule` as thin bootstraps over the upstream C++, compiled from the installed npm package and not vendored. A Nitro HybridObject cannot answer the registry lookup, and an empty TurboModule would hide failures, so a method the platform does not implement returns an error. New third-party TurboModule names need their own ADR. `QtReactHost::addTeardownHook` lets a library stop its thread or runtime while Hermes is still alive.

Worklets evaluates serialized function source on its secondary runtime even when the app bundle is bytecode. An app with Worklets on therefore links the full `libhermesvm.so` from `RNQNX_HERMES_QNX_DIR`. A release app without Worklets keeps `libhermesvmlean.so`, and a missing full VM stops configuration. Bundle Mode is not supported. The Worklets Babel plugin comes from `babel-preset-expo` when the package is installed.

The platform patches upstream C++ in generated copies with one-line text substitutions that fail the configure step if the upstream line changes: one `AsyncQueueImpl.cpp` line (`pthread_setname_np` takes the thread first on QNX), the `SynchronouslyUpdateUIPropsFunction` type and the loop that applies synchronous props.

## Reanimated and Gesture Handler

`QnxReanimatedModule` builds the upstream `ReanimatedModuleProxy` with Qt implementations of `requestRender` (the frame bridge), `getAnimationTimestamp` (`steady_clock`) and `synchronouslyUpdateUIPropsFunction` (a GUI-thread update into the mounted item). Events for `useAnimatedScrollHandler` and gesture handlers come through `Scheduler::addEventListener`, and the handler worklet runs on the UI thread. Sensors, keyboard, pseudo-selectors and platform CSS backends are not provided, and sensors and keyboard log and return -1.

The recognizers are in `vnext/src/gesture/GestureHandlerCore.cpp`, a registry with no Qt or React dependency. `QtGestureInput` observes window mouse and touch events and never consumes them, so `Pressable` keeps working beside it (see [Input path](/docs/explanation/input-path)).

| Handler                        | Status                                                                                                                           |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| Pan, Tap, LongPress, Fling     | Implemented with the options the source lists, for example Pan min distance, offsets and velocity, Tap count, duration and delay |
| Manual                         | Driven by `GestureStateManager`                                                                                                  |
| Pinch, Rotation, Native, Hover | Accepted, then fail on the first pointer with a log line                                                                         |

By default the first handler to activate fails every other begun or active handler that shares a pointer. `simultaneousHandlers`, `waitFor` and `blocksHandlers` change that. Pointer-data callbacks, multi-pointer pan averaging, hit slop, `RNGestureHandlerButton` behavior (it mounts as a plain container), arbitration with Qt scrolling and coordinate spaces for transformed ancestors are not implemented.

## Teardown

At shutdown the platform stops frames, marks the RN runtime dead, invalidates the proxy and joins the UI thread. Queued but unstarted jobs are discarded. In the Pi 400 probes of 2026-11-13, five of five runs exited with status 0 and logged `RNQNX_WORKLETS_SHUTDOWN_OK`, with a never-ending frame loop, 500 queued UI jobs and 2000 queued UI-to-JS posts. Gesture cancellation is specified separately: detaching, disabling or moving a handler cancels its current contact first, and window deactivation cancels all handlers. A 24-case native suite covers this on Linux (`docs/evidence/pr149-cancellation-2026-11-17/README.md`).

## Limits

- **Busy JavaScript.** React runs on the GUI thread, so a blocked JS thread stops repainting and stops frame callbacks. The device probe reported `JS busy 300 ms: 0 of 40 UI worklet jobs ran inside the busy window`, so no run shows UI-thread work continuing while JS is blocked. The remedy named in the docs is a dedicated JS thread with a free GUI thread (`docs/platform-modernization/01-runtime-baseline.md`), and the work has not been done.
- **Input source.** The pan, tap and double-tap results used injected single-pointer events from `rnqnx-inject` at 1024x768. Pinch, rotation, multi-pointer input, 1920x1080 and a physical mouse are not verified.
- **Scope of the hosted evidence.** The linked Linux host fixture (Qt 6.11.1, software rendering) moves one view by 60 px with `withTiming` and another by 40 px with a pan, and repeats the flow over two hosts and a teardown with a pending frame. It qualifies host linkage and does not stand in for the QNX binary.
- **Unavailable pieces.** `toggleSlowAnimationsOnUIRuntime` returns false, and general animated SVG props and broader hook compositions are listed as open in `docs/handoff/CURRENT_STATE.md`.
- **Release builds.** Source unpackers need a Hermes that compiles source, so a release build needs the bytecode unpacker path (`hermesBytecode: true`) proved on the target. This was proved only on full Hermes.

Release gates for this stack stay pending. See [Release gates](/docs/reference/release-gates) and [Known gaps](/docs/reference/known-gaps), and [Threading model](/docs/explanation/threading) for the owner-thread rules the seams above enforce.
