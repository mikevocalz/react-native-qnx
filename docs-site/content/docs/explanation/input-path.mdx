---
title: Input path
description: How a key press or pointer event on a QNX device travels from the USB driver through Screen and Qt to a JavaScript handler, and which hops have device evidence.
---

A tap, click, key press or mouse wheel notch passes through six hops on the way to JavaScript. Four of them are QNX and Qt code that the project configures and does not own. Two are project code: `QtTouchDispatcher` and the TextInput bridge. This page names each hop, shows what the repository proves about it, and lists the hops that no test has exercised with real hardware.

All device results below come from one board, a Raspberry Pi 400 running QNX 8.0.0 (`qnxpi`, display 1024x768 in the November 2026 runs). Nothing here was run on another device.

## Hop 1 and 2: USB to Screen

At boot, `/system/etc/startup/full_startup.sh` starts the USB stack (`usb_start.sh`, `usblauncher_otg`) and then `io-hid -dusb`. The script runs `chown 36 /dev/io-hid/io-hid`, so members of group 36 (`screen`) can read keyboard and mouse events. Apps run as `qnxuser`, who is in that group. The Pi 400 image runs `pi400-recover.sh` as `post_start`, which skips the stock USB block, so these lines live in `full_startup.sh` ([Run a React Native app on the Pi 400 desktop](https://github.com/mikevocalz/react-native-qnx/blob/main/docs/getting-started/pi400-desktop-app.md)).

I found no evdev code in `vnext/`, `native/` or `packages/`. On this path `io-hid` supplies events to QNX Screen, and the Qt platform plugin reads them from Screen. Source for `io-hid` itself is not in the repository.

When no mouse pointer appears or clicks do nothing, the first check is `ls -l /dev/io-hid/io-hid`. The node must exist with owner 36. A missing node means `io-hid` did not start (`/tmp/pi400-usb.log`), and a mouse plugged in before `io-hid` came up needs to be re-plugged. These steps come from the troubleshooting section of the desktop guide. The run logs show the node present and `io-hid=0` at the start of the PR 149 runs (`docs/evidence/pr149-pi400-run2-2026-11-19/run.txt`).

## Hop 3: Screen to Qt events

Screen picks the window under the pointer, converts the position to window coordinates and sends the event to that window's owner. Qt's QNX platform plugin (`qqnxscreeneventhandler.cpp` in Qt 6.12.0) converts the event to a Qt event. For keys, it passes `flags & SCREEN_FLAG_KEY_REPEAT` to `QWindowSystemInterface::handleExtendedKeyEvent` as the auto-repeat argument (`docs/evidence/pr149-pi400-keyhold-2026-11-19/README.md`). The plugin also reports a mouse wheel notch as 10 angle units instead of 120, according to the desktop guide, which says the project scales for this so ScrollView, FlatList and SectionList move 100 px per notch over 120 ms. I did not find that wheel code in `vnext/` or `native/` in this checkout, so the wheel behavior rests on the guide's statement alone.

## Hop 4: the touch dispatcher

`QtTouchDispatcher` (`vnext/src/fabric/QtTouchDispatcher.cpp`) is a `QObject` event filter on the Qt Quick window. It handles two input shapes.

**Mouse.** A left-button press, move and release become one touch with identifier 0. `QMouseEvent::position()` gives the page point, `item->mapFromScene` gives the offset inside the target view, and the Qt millisecond timestamp becomes the touch timestamp. On release, the ending contact appears only in `changedTouches`. The source comment explains why: otherwise React never releases its responder.

**Touch.** `QTouchEvent` points keyed by `point.id()` keep a set of active touches. `makeTouchEvent` fills `touches` with every active touch, `targetTouches` with those that started on the same view, and `changedTouches` with the one that changed.

Both shapes call `hitTest`. It first checks registered input shields, then picks the topmost root surface (a LogBox surface added later wins), then walks down `deepestItemAt`. That walk sorts children by `z`, takes the last visible child that contains the point and skips items that carry the `rnqnxInputTransparent` property. The item is mapped back to a React tag by looking it up in the emitter registry. When the SVG renderer is built in, an `<Svg>` root asks its own `hitElement` which element is under the point, because an `<Svg>` paints all its elements into one item.

A claimed JavaScript responder wins over the hit test for the rest of a gesture (`responderTag_`, set through `setJsResponder`). The dispatcher then calls the `TouchEventEmitter` methods, and the events reach React through the host's `EventBeat`.

### Input lifecycle option

The opt-in CMake option `RNQNX_ENABLE_INPUT_LIFECYCLE` (default OFF) turns on cancellation. With it, the dispatcher cancels active touches on `QEvent::TouchCancel`, `WindowDeactivate` and `UngrabMouse`, cancels a touch whose target view was removed, ignores non-left buttons and second mouse presses, and the host sets `__RNQNX_INPUT_LIFECYCLE__` so an RN patch forwards a null-target `topTouchCancel`. Without the option, the dispatcher keeps the original single-pointer mouse path.

## Hop 5: keys and TextInput

Key events go to the Qt Quick item that has active focus. The TextInput wrapper in `vnext/src/views/qt/QtTextInputQml.cpp` is a `FocusScope` around a QML `TextInput` or `TextEdit`. Its `Keys.onPressed` handler records the key text (`mapKeyText` maps Backspace to an empty string, Return and Enter to a newline, Tab and Backtab to a tab, Escape to `\x1B`) and emits `keyPressed()`. `QtTextInputBridge` connects that signal and the text, selection, submit and focus signals, then sends them to React as Fabric events. Each edit carries an event count, and `applyJS` rejects a JavaScript write whose count is stale. In contract mode (`RNQNX_ENABLE_TEXT_INPUT_CONTRACT`, default OFF), each editable wrapper is one tab stop through `setActiveFocusOnTab`.

Modal and drawer dismissal use Qt keys directly. `QtModalQml.cpp` declares `Keys.onEscapePressed`, and run 2 on the Pi closed both a modal and a drawer with an injected Escape (`docs/evidence/pr149-pi400-run2-2026-11-19/README.md`).

## Hop 6: gestures

`QtGestureInput` (`vnext/src/gesture/QtGestureInput.cpp`) installs a second event filter on the window. It forwards left-button mouse events whose source is `Qt::MouseEventNotSynthesized`, touch points and cancel events to the recognizer `Registry`, and it returns `false` for every event. The dispatcher still sees them, so Pressable and Gesture Handler can respond to the same press. The source states that arbitration with Qt scrolling is not implemented. The [animation runtime](/docs/explanation/animation-runtime) page covers what happens after the Registry decides.

## Where the evidence stops

Every input event in these receipts is synthetic. The Pi 400 runs used `tools/qnx-input/rnqnx-inject`, which creates its own pointer and keyboard devices with `screen_create_device_type()` and injects events through Screen. Three details of the injector came from failures. Without `SCREEN_FLAG_POSITION_VALID` in `SCREEN_PROPERTY_FLAGS`, Screen places the pointer at 0,0 and Qt sees a position outside the window. Without a device, Screen cannot find the window under the pointer. Screen leaves the timestamp at 0, so every pair of clicks read as a double click until the injector set one.

That design skips hops 1 and 2. The receipts say so directly:

- Run 1: "All input came from `rnqnx-inject*` through Screen, not a physical keyboard or mouse." Run 2 lists "A real keyboard held down" under not verified.
- The held-key run: "A real USB keyboard held down ... the real keyboard path (`io-hid`) was not exercised."
- The TextInput receipts: "no physical keyboard/HID, language engine, software IME or assistive technology session is claimed."

The USB path through `io-hid` has boot-script and troubleshooting documentation, and the node was present on the board during the runs. Whether a physical USB mouse or keyboard produces the same Screen events as the injector is not verified in this repository. Other unverified items are multi-pointer touch, a keyboard-scrolled list (the held key moved a focus ring, not a ScrollView), the step counts of the held-key test (arithmetic from injector timing, not logged by the app), and the first `key tab` after a click, which showed no visible ring change.

See also [Threading model](/docs/explanation/threading) for the thread that runs these callbacks, and [Component matrix](/docs/reference/component-matrix) for per-component status.
