[CONTRIBUTING.md](https://github.com/mikevocalz/react-native-qnx/blob/main/CONTRIBUTING.md) says to publish no package and create no release tag until the real-device acceptance gate for the claim has passed. It also says the `@rn-qnx` scope stays provisional until the owner names the publishable npm organization. Independent release-please releases start once real package manifests, owners and that organization exist. Until then, a `0.1.0` in a manifest does not mean a published or supported release.

Its header says package-specific changelogs begin when package manifests and independent release units exist. The [changelog page](/docs/reference/changelog) lists merged pull requests generated from git history.

## What v1 means here

[The readiness record](https://github.com/mikevocalz/react-native-qnx/blob/main/docs/releases/v1-readiness.md) calls v1 "a release milestone for the RN 0.88 line". It adds three limits:

- v1 does not imply a stable Nitro ABI. The exact Nitro v1 alpha stays pinned (`1.0.0-alpha.nightly.136.gdb81de61bd32` in the [compatibility matrix](https://github.com/mikevocalz/react-native-qnx/blob/main/docs/getting-started/compatibility-matrix.md)).
- Package versions stay at their existing values until package ownership, release units and publication are reviewed.
- The preparation work does not tag or publish a release.

v1 is defined by eleven gates in [v1-readiness.json](https://github.com/mikevocalz/react-native-qnx/blob/main/docs/releases/v1-readiness.json): distribution, ci, cold-boot, device-parity, performance, developer-path, documentation, app-identity, window-chrome, expo and dependencies. I ran `jq -r '.. | objects | select(has("id") and has("status")) | "\(.id) \(.status)"'` on that file. All eleven print `pending`. The [release gates page](/docs/reference/release-gates) shows the same table.

`pnpm validate:v1` exits nonzero unless every required gate is passed with a repository evidence path (stated in the readiness record; I did not run it). A reviewer has to inspect the cited revision and result before changing a gate.

## Supported React Native and Expo versions

The project targets one line. The direct pins in the [compatibility matrix](https://github.com/mikevocalz/react-native-qnx/blob/main/docs/getting-started/compatibility-matrix.md) are:

| Component       | Pinned version          |
| --------------- | ----------------------- |
| React Native    | `0.88.1`                |
| React           | `19.3.0`                |
| Expo            | `58.0.26` (Expo SDK 58) |
| Metro           | `0.87.1`                |
| Hermes compiler | `260318099.0.5`         |
| Node            | `>=26.0.0`              |
| pnpm            | `pnpm@12.21.0`          |

The matrix holds two upgrades on purpose. React stays at `19.3.0` because React Native 0.88.1 ships a renderer built from React `19.3.0`. Metro stays at `0.87.1` because React Native 0.88.1 depends on `^0.87.1`. The matrix also says these versions do not imply upstream QNX support. [ADR-0008](https://github.com/mikevocalz/react-native-qnx/blob/main/docs/adr/0008-version-pinning.md) covers version pinning, and [CONTRIBUTING.md](https://github.com/mikevocalz/react-native-qnx/blob/main/CONTRIBUTING.md) requires exact direct pins and a frozen pnpm lockfile.

The Expo SDK 58 package support list is generated and checked by `pnpm validate:expo-sdk58-support` ([package.json](https://github.com/mikevocalz/react-native-qnx/blob/main/package.json)). Expo Go is not supported ([ADR-0006](https://github.com/mikevocalz/react-native-qnx/blob/main/docs/adr/0006-expo-dev-builds.md)).

No other React Native or Expo version is mentioned as supported. Treat any other version as untested.

## Support and deprecation policy

The repository has no support window, no deprecation policy and no compatibility promise across versions. The nearest statement is in [SECURITY.md](https://github.com/mikevocalz/react-native-qnx/blob/main/SECURITY.md): the project is experimental, the active RN 0.88 development line receives security fixes as maintainers can verify them, and no supported production release or response-time guarantee exists. The [FAQ](/docs/faq) answers "Is it ready for production?" with no.

## Proposed versioning scheme

This section is a proposal. The repository records no decision on it, and the owner has not accepted it. It uses only facts stated above: the root workspace and all 12 packages sit at `0.1.0`, there are no tags, and v1 is "a release milestone for the RN 0.88 line".

- **One version line for the whole repository.** The root `package.json` `version` is the number of the repository. Package manifests move with it until package ownership and release units are reviewed, which [CONTRIBUTING.md](https://github.com/mikevocalz/react-native-qnx/blob/main/CONTRIBUTING.md) already requires before independent releases.
- **Semantic versioning, `0.x` until v1.** Before v1, a minor bump may break the API. `1.0.0` is tagged only when all eleven gates in the readiness record are passed.
- **Tags are `v<major>.<minor>.<patch>`.** Pre-release tags use a suffix such as `v1.0.0-rc.1`. A tag is created only after the gate evidence for the claim exists, as CONTRIBUTING.md says.
- **The React Native line is part of the release note, not the version.** Each release states its pinned React Native, React, Expo and Hermes versions from the compatibility matrix. A move to a new React Native line starts a new minor (or major after v1) and a new snapshot of these docs.
- **Docs follow the tag.** `latest` is `main`. Each tag gets a frozen copy of this site.

## Versioned docs

The site has a version selector in the header. It reads two files at build time:

| Source                                       | What it provides                                                                                                     |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `version` in the repository's `package.json` | The number in the label of the first entry, "latest (main, 0.1.0)". The label changes when the root version changes. |
| `docs-site/versions.json`                    | The frozen copies. Each entry is a release tag and links to `/v/<tag>/docs`.                                         |

Today `versions.json` lists no snapshots, because no tag exists, so the selector shows one entry and is disabled. No release was invented to fill it. The procedure for adding a snapshot at a tag is in [Contributing](/docs/contributing#snapshot-the-docs-at-a-release-tag).

The `documentation` gate in the readiness record ("Versioned v1 documentation") is pending. It asks for versioned getting-started pages, API and support limits, an evidence gallery, ADRs and release notes. The selector and the snapshot procedure give it the versioning mechanism. The gate stays pending until a v1 snapshot exists and a reviewer inspects it.

## Where to report problems

Security reports go through [SECURITY.md](https://github.com/mikevocalz/react-native-qnx/blob/main/SECURITY.md):

- Use [GitHub private vulnerability reporting](https://github.com/mikevocalz/react-native-qnx/security/advisories/new) when it is available.
- If it is not, open a minimal issue that asks the owner for a private contact. Leave out exploit details, target addresses, credentials and licensed files.
- Include the affected revision, dependency versions, host and target identity, reproduction steps, observed impact and a small sanitized reproducer. Label host, QNX VM and physical-board results separately.

For other bugs, CONTRIBUTING.md names no bug tracker, issue template or reporting procedure, and `.github/` holds no issue templates (`ls .github/ISSUE_TEMPLATE` found nothing). It describes how to contribute changes: follow the architecture locks, Conventional Commit subjects, and the handoff files in `docs/handoff/`. See [contributing](/docs/contributing). Do not claim a QNX build or runtime result in a report without the host, target, command, exit status and evidence, as CONTRIBUTING.md requires of changes.
