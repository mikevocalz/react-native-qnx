title: Architecture
description: The layers between your JavaScript and the QNX screen, which source file implements each one, and what the project has verified on a device.
---

react-native-qnx runs React Native on QNX with Hermes as the JavaScript engine, React Native's Fabric renderer as the UI core, and a Qt Quick item tree as the view backend. This page names each layer, the class that implements it, and the evidence behind it. The renderer lives in `vnext/`, not in `native/`. The `native/` tree holds the Qt modules that sit beside it (`native/qt/*`), the window chrome (`native/window-chrome`), the lifecycle observer (`native/lifecycle`) and the QNX Screen probe (`native/platform/qnx`).

## Hermes and the bridgeless host

`QtReactHost` owns the Hermes runtime, the `RuntimeScheduler` and React Native's `Scheduler`. React Native ships a generic host only for Android and Apple, so this class supplies the pieces that platforms normally provide: an `EventBeat`, a component registry, a `SchedulerDelegate`, timers and platform constants. Before a bundle runs it sets `RN$Bridgeless` to true and installs an empty `__fbBatchedBridgeConfig`, because React Native's JavaScript checks both. There is no legacy bridge and no Paper view manager.

Core React Native JavaScript calls `TurboModuleRegistry.getEnforcing` for its own modules. `QtReactHost::installTurboModuleBinding` answers those calls with React Native's default C++ modules plus QNX ones: `QnxDeviceInfo`, `QnxSourceCode`, `QnxExceptionsManager`, `QnxImageLoader`, `QnxWebSocketModule`, `QnxFileReaderModule`, `QnxSegmentFetcher`, a native Animated module driven by a 16 ms `QTimer`, and `QnxAppStateModule` when `RNQNX_ENABLE_APP_STATE` is on. A name nobody provides returns null, so `getEnforcing` fails with that module's name. Application-facing native APIs use Nitro instead. [Threading](/docs/explanation/threading) covers how Nitro callbacks get back onto the JavaScript thread.

## Fabric and the component registry

`makeComponentRegistryFactory` registers these descriptors: Root, View, Paragraph, Text, RawText, Image, ScrollView, TextInput, ActivityIndicatorView, Switch, SafeAreaView and ModalHostView. Optional libraries add their own through `QtReactHost::addComponentDescriptorProvider`, which must run before the first host is constructed. The Switch descriptor reuses React Native's Apple shadow node, and `vnext/src/fabric/SwitchShadowNode.cpp` supplies its name and a 51 by 31 default size because the Apple `.mm` files do not build here.

A component without a QML mapping fails its `Create` mutation with `MountError::UnknownComponentType`. The adapter does not fall back to a generic view. The next page, [Render lifecycle](/docs/explanation/render-lifecycle), follows a commit from JavaScript to Qt items.

## Qt Quick as the view backend

Qt Quick supplies a retained item tree, shaped text, images and input in one C++ event loop. `QtQuickItemFactory` compiles one `QQmlComponent` per React Native component type from inline QML source and caches it. `QtQuickMountingLayer` keeps a map from Fabric tag to `QQuickItem`, creates items unparented, and deletes them itself (the factory sets C++ ownership). ADR-0002 still lists its Pi 400 1,000-item benchmark and some source-ownership checks as open.

In the playground host (`vnext/probes/playground/main.cpp`) the `View` type is a QML `Item` with `clip: true`, a `Rectangle` for background and border, and a `Shape` for per-corner radii. `Text` is a Qt Quick `Text`, `ScrollView` is a `Flickable` with a `WheelHandler`, and `Image` is a Qt Quick `Image` with a loading-indicator child. Optional modules register more types: `native/qt/svg`, `native/qt/rnsvg`, `native/qt/video`, `native/qt/nativeui` (drawer and tab bar) and the Expo image view in `vnext/src/views/qt/image`.

Layout comes from Yoga, and Qt items are absolute leaves ([ADR-0001](https://github.com/mikevocalz/react-native-qnx/blob/main/docs/adr/0001-qt-quick-backend.md)). [Layout](/docs/explanation/layout) explains how the geometry reaches each item.

## The window

The host creates a `QQuickWindow`, mounts the surface into `window.contentItem()` (or into `WindowChrome::contentRoot()` when the window chrome is on), and runs `QGuiApplication::exec`. Qt's QNX platform plugin sits between that window and QNX Screen. The direct-Screen executable `rnqnx_playground` (`native/platform/qnx/application/main.cpp`) fills a buffer with a solid color and is a toolchain probe. It is not a component backend. GTK4 was viable and was rejected to avoid a second object model ([ADR-0001](https://github.com/mikevocalz/react-native-qnx/blob/main/docs/adr/0001-qt-quick-backend.md)).

## Data flows in two directions

Downward, a React commit becomes Fabric mutations and then Qt item changes. Upward, Qt pointer events go through `QtTouchDispatcher`, which hit-tests the item tree and calls the matching shadow view's `TouchEventEmitter`. Item signals (scroll position, text changes, switch values, image status) go through small bridge objects to their emitters. `QtEventBeat` tells React Native when to run queued events by posting `induce()` to the Qt event loop. The route from hardware to JavaScript, with its device evidence, is on the [input path](/docs/explanation/input-path) page.

## Verified and not verified

- A real React Native Hello World rendered through Fabric, Hermes and Qt Quick on a Raspberry Pi 400 under QNX 8.0.5 on 2026-11-07 (`docs/evidence/pi400-hello-world-2026-11-07.txt`). That receipt records no frame rate, startup time or memory figure.
- `tests/cpp/ShadowTreeMountingHostTest.cpp` commits a real `ShadowTree` and checks Yoga geometry on Qt items (fixed sizes, flex distribution, padding, in-place resize, unmount). `tests/cpp/QtReactHostHostTest.cpp` and `tests/cpp/QtQuickMountingLayerHostTest.cpp` cover the host and the item layer. These are host tests.
- Per-component device status is in the [component matrix](/docs/reference/component-matrix), and open items are in [known gaps](/docs/reference/known-gaps).
- The Qt Quick render loop (threaded or basic) is not set anywhere in this repository. Which one the Pi 400 build uses is not verified.

Skia was the first renderer choice and is superseded ([ADR-0003](https://github.com/mikevocalz/react-native-qnx/blob/main/docs/adr/0003-skia-initial-renderer.md)). Hermes is the only supported engine. All decisions are in the [architecture decision index](/docs/explanation/adr-index).
