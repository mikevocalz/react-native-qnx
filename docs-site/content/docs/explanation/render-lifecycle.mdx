---
title: Render lifecycle
description: What happens between a React state change and pixels on a Qt Quick window, from the JavaScript render through the Fabric commit and mount to the next frame.
---

A React update reaches the screen in six steps: React renders in JavaScript, Fabric commits a new shadow tree and runs Yoga, the scheduler announces the transaction, `QtSchedulerDelegate` pulls it, `ShadowViewMutationAdapter` turns its mutations into Qt item changes, and Qt Quick draws the next frame. Steps one through five run on the owner thread described in [Threading](/docs/explanation/threading). This page follows that path using the class and method names in `vnext/`.

## Startup

The host builds one `QtReactHost`, then runs these calls in order (`vnext/probes/playground/main.cpp`): `installTurboModuleBinding`, `installComponentProvider`, `installPlatformConstants`, `installTimers`, `evaluate` the bundle, `startSurface`, `setWindowSize`.

`startSurface` creates a `SurfaceHandler`, registers it with the `Scheduler`, sets props and layout constraints, and starts it. `UIManager::startSurface` then hops the runtime executor and calls `RN$AppRegistry.runApplication`, which makes React render the first tree. `evaluate` must return before this point, so the bundle has already registered the app component.

## 1. React renders

A state update runs inside a `RuntimeScheduler` task. React reconciles and drives `nativeFabricUIManager`: `createNode` for new host nodes, `createChildSet` and `appendChildToSet` to collect the surface's children, then `completeRoot`. Those calls build `ShadowNode` objects in C++ with their props and event emitters. `QtReactHost::hasFabricUIManager` checks that this global exists.

## 2. Fabric commits

`completeRoot` commits the new root into the surface's `ShadowTree`. During the commit Fabric runs Yoga over the tree (see [Layout](/docs/explanation/layout)) and diffs the result against the previous revision. The diff yields a list of `ShadowViewMutation` values of type `Create`, `Delete`, `Insert`, `Remove` or `Update`, held by the surface's `MountingCoordinator`. The coordinator keeps at most one pending revision. `tests/cpp/ShadowTreeMountingHostTest.cpp` commits a real `ShadowTree` and checks the mounted geometry, and `tests/cpp/QtReactHostHostTest.cpp` commits through `QtReactHost::commit`.

## 3. The scheduler announces the transaction

`schedulerDidFinishTransaction` fires synchronously on the committing thread and does nothing in `QtSchedulerDelegate`. Mounting waits for `schedulerShouldRenderTransactions`, which React Native dispatches as a rendering update on the `RuntimeScheduler`. That puts the mount after the current JavaScript task and its microtask checkpoint. If the call arrives on a thread other than the owner, `onOwnerOrPost` posts it to the owner thread first.

## 4. The delegate pulls one transaction

`schedulerShouldRenderTransactions` makes one `pullTransaction()` call per notification. It does not loop. The source comment explains why: with a `MountingOverrideDelegate` installed, Reanimated's layout-animation proxy answers every pull with a transaction, and a `while` loop spun at full CPU on the first screen that mounted a Reanimated component. Every later commit or animation frame notifies again.

## 5. The adapter applies mutations

`ShadowViewMutationAdapter::apply` walks the list in React Native's order. A failure is recorded and the walk continues, because stopping halfway would leave the item tree further from the shadow tree than finishing does. What each mutation does:

| Mutation | Adapter behavior |
| --- | --- |
| `Create` | Look up the QML type mapped to the component name. Create the item unparented through `QtQuickMountingLayer::create`. Apply the first layout and props in one pass: `updateLayout`, `onLayout` if subscribed, emitter registration with `QtTouchDispatcher`, signal connections (scroll, TextInput, Switch, Image, Modal), then text, image, TextInput, ActivityIndicator, Switch, SVG and extra-component props, then `updateStyle`. Doing all of it here avoids a frame at the origin with zero size. |
| `Insert` | `QtQuickMountingLayer::insert` parents the item (into `contentItem` for a `Flickable`) and orders it among Fabric siblings with `stackBefore`. Indices count only Fabric children, so QML-owned backgrounds do not shift them. Then `updateScrollContentSize` on the parent. |
| `Remove` | Detach the item without destroying it, then update the parent's scroll content size. The index must agree with the item's position. |
| `Delete` | Drop the tag from the adapter's maps and the touch dispatcher, notify the view observer, then `destroy` the item. `destroy` detaches a still-mounted item first, and refuses to delete a borrowed root. |
| `Update` | Re-register the emitter, `updateLayout`, `onLayout` if subscribed, reconnect signals, reapply props and `updateStyle`, then refresh the parent's scroll content size. |

Failures use the `MountError` values in `QtQuickMountingLayer.h`: `UnknownComponentType`, `DuplicateTag`, `UnknownTag`, `UnknownParent`, `NotAChildOfParent`, `IndexOutOfRange`, `ItemCreationFailed`, `UnsupportedTextInput` and `UnsupportedAccessibility`. The delegate prints each as `RNQNX_MOUNT_FAILURE type tag error detail` on stderr. A failed `Create` can leave a view and its subtree off screen with no other trace, so check that log first when something is missing.

## 6. Mount acknowledgement

When the transaction applied with no failures, the delegate calls `UIManager::reportMount` through the mount reporter. Mount hooks, including Reanimated's, resume commits only after this. The delegate never acknowledges a partly failed mount.

## 7. The frame

Property changes on `QQuickItem` mark items dirty. Qt Quick synchronizes the scene graph and renders on its next frame, with no further call from this code. The mount returns without waiting for the frame. `QtFrameBridge` runs worklet frame callbacks at `QQuickWindow::afterAnimating`, before the scene graph syncs, so worklet writes land in the following sync. Which render loop Qt uses on the Pi 400 is not verified.

## Updates that skip the commit

- **Commands.** `schedulerDidDispatchCommand` calls `ShadowViewMutationAdapter::dispatchCommand` for imperative calls such as `ScrollView.scrollTo` and `scrollToEnd`, which set `contentX` and `contentY` on the `Flickable`. The `animated` argument is accepted and ignored.
- **Native-driven animation.** `schedulerShouldSynchronouslyUpdateViewOnUIThread` calls `synchronouslyUpdateViewOnUIThread`, which applies a prop delta (opacity, transform) straight to the mounted item without a commit. A 16 ms `QTimer` drives the Animated module that produces these.

## Events returning

Qt items report back through bridge objects (`QtTextInputBridge`, `QtImageBridge`, `QtSwitchBridge`, `QtModalBridge`) and through `QtTouchDispatcher`, all of which call shadow-view event emitters. React Native queues those events and runs them when `QtEventBeat` induces a beat. The hit-testing and device evidence are on the [input path](/docs/explanation/input-path) page. `QtTouchDispatcher` is constructed by the playground host only when `RNQNX_ENABLE_INPUT_LIFECYCLE` is on, and that CMake option defaults to OFF.

## Resize and teardown

`resizeSurface` calls `constraintLayout` with the new size. Fabric lays the tree out again and the same mount path runs. Nothing remounts.

`stopSurface` stops the `SurfaceHandler`. That calls `UIManager::stopSurface`, which requires `global.RN$stopSurface`. A real bundle defines it, and `startEmptySurface` installs a no-op for surfaces with no app. Stopping produces an empty-tree commit, so `Delete` mutations arrive while the host is being destroyed. The touch dispatcher must outlive that commit for this reason.
