Three consumers load pictures on the Qt host: the React Native `Image` API through the `ImageLoader` module, the `expo-image` view (`ExpoImageItem`), and `<Image>` elements inside an RNSVG `<Svg>`. They share one admission queue, one decoded-picture cache and one disk cache. This page follows a request through those parts and lists which steps have device evidence. The source of truth is `docs/image-loader.md` and the receipts under `docs/validation/pr159-*`.

## Three entry points, one queue

`QnxImageLoader` (`vnext/src/runtime/QnxImageLoader.cpp`) is the React Native `ImageLoader` module. It backs `Image.getSize`, `getSizeWithHeaders`, `prefetch`, `prefetchWithMetadata` and `queryCache`. It also carries the functions `expo-image` needs: `loadImage`, `releaseImage`, `generateBlurhash`, `generateThumbhash`, `writeToCache`, `readFromCache`, `configureCache`, `clearMemoryCache`, `clearDiskCache` and `getCachePath`. The package `@rn-qnx/expo-image-qnx` wraps them as the `ExpoImage` module (`packages/expo-image-qnx/README.md`).

`ExpoImageItem` (`vnext/src/views/qt/image/ExpoImageItem.cpp`) is a `QQuickPaintedItem`. It picks a source from the `source` array, loads it itself, decodes on a worker and paints with `QPainter`. It uses no `QtQuick.Effects` or shader, because the Pi's Qt runtime ships neither. Animated GIF and WebP play through `QMovie` when the Qt build has the format plugin. A source that is an `ImageRef` skips loading and reads from `ImageRefRegistry`.

`QtRnsvgImageProvider` (`vnext/src/fabric/QtRnsvgImageProvider.cpp`) serves `<Image>` elements inside an `<Svg>`. It calls `QtImageCache::loadImage`, which returns decoded pixels and original dimensions whether or not the cache retains the entry. Without that, a private or no-store response, an image larger than the cache budget, or a memory clear during a load made the SVG image fail only because no cached entry remained. The SVG adapter forwards no caller headers.

All three go through `ImageFetchQueue` (`vnext/include/react-native-qnx/views/image/ImageFetchQueue.h`), which admits `kSharedConcurrency = 6` tasks at a time. The `priority` prop of `expo-image` (`low`, `normal`, `high`) decides which waiting fetch starts next, and cancelling a waiting task removes it.

## Workers and thread ownership

JavaScript runs on the Qt owner thread (see [Threading model](/docs/explanation/threading)). Image work follows one rule: worker closures hold native values only, and anything that touches a Promise, the `ImageRefRegistry` or an event runs on the owner thread.

`ImageTaskQueue` (`vnext/include/react-native-qnx/views/image/ImageTaskQueue.h`) runs computation on a `QThreadPool` behind the same admission queue. Decoding, resizing, tinting, BlurHash and ThumbHash encoding, PNG encoding, explicit cache writes and disk-cache reads all run there. An `ImageRef` is copied into a native snapshot when its task is admitted, so releasing the JavaScript source while the task waits is safe. `releaseImage` stays synchronous.

Cancelling a task has a detail that took two fixes to get right. A cancelled or abandoned worker keeps its admission slot until its physical file or disk read finishes, so repeated teardown cannot pile unbounded blocked reads behind the queue. The receipt `docs/validation/pr159-fetcher-admission-2026-11-16.md` records a test that keeps two real file reads blocked in empty FIFOs, destroys their fetcher, and shows a third image completing despite the two-slot limit in the original code. A second fix drops owner callbacks before admission starts a successor, since the successor may itself destroy the owner.

## Caches and their epochs

| Cache | Class | Limit | Notes |
| --- | --- | --- | --- |
| Decoded memory | `DecodedImageCache` | 32 MiB by default, LRU | Shared by `Image` and `ExpoImageItem`. Qt Quick resolves an already-prefetched URI to `image://rnqnx/cache/...` instead of downloading it again. |
| Disk | `ImageDiskCache` | 128 MiB by default, least recently used first | One file per key, named by the key's SHA-256. The key is the URI plus headers, or the `cacheKey`. |

Memory and disk each carry a generation counter, so a clear takes effect at once without waiting for in-flight work.

- `clearMemoryCache` advances the memory generation and clears the LRU on the owner thread. Loads admitted earlier still deliver their pixels and dimensions, but pending view decodes, core prefetches and explicit writes check the generation under the same mutex and do not refill the cleared cache.
- `clearDiskCache` advances the disk generation immediately and sweeps files on a worker. A read or a newer write applies any pending sweep first, so a delayed sweep cannot delete a newer file. A failed sweep resolves `false`, stays pending and keeps old entries hidden.
- The two clears do not affect each other.
- `queryCache` returns `"memory"` only for entries actually retained. There is no HTTP revalidation: entries live until LRU eviction or process exit, so changing resources need versioned URLs.

## Formats and plugins

Qt Quick on this build decodes only PNG until image plugins exist. The Pi 400 receipt `docs/evidence/pi-image-formats-2026-11-13.md` measured `QImageReader::supportedImageFormats()` on the board:

| Plugins present | Formats |
| --- | --- |
| Runtime only plus app GIF and JPEG | `bmp gif jfif jpeg jpg pbm pgm png ppm xbm xpm` |
| Above plus `qtimageformats` | adds `icns tga tif tiff wbmp webp` |

WebP was missing until `scripts/qt-public/build-imageformats-qnx.sh` built the `qtimageformats` module against the QNX qtbase (201 build steps, exit 0 in that receipt). The release launcher sets `QT_PLUGIN_PATH=$APP_DIR/plugins:$QT_ROOT/plugins`, so the app directory carries `plugins/imageformats` (`libqgif.so`, `libqjpeg.so`, `libqwebp.so` and the rest). `svg` appears in neither list, because `libqsvg.so` comes from a Qt module the Qt build does not include. SVG documents render through the project's own RNSVG renderer, not through `QImageReader`.

## Remote URLs and TLS

`QtImageFetcher` (`vnext/src/views/qt/image/QtImageFetcher.cpp`) sets manual redirect handling and disables automatic cookie load and save. It follows at most five redirects under the original deadline. Same-origin hops keep caller headers, and an origin change drops them. It rejects non-HTTP(S), credential-bearing and HTTPS-to-HTTP targets. A request times out after 30 seconds, and an encoded body over 16 MiB (`kMaxEncodedBytes`) is refused. `ImageDecode.h` rejects images over 16 Mi pixels (`kMaxDecodedPixels`, 16 * 1024 * 1024) after reading the dimensions and before allocating.

HTTPS needs Qt's TLS backend plugin. Qt 6 loads it from `plugins/tls/`, and the first staged runtime had none, so every `https://` request failed. The fix builds the OpenSSL backend (`libqopensslbackend.so`) from public Qt source. It loads the board's `/usr/lib/libssl.so.3` at run time and reads certificates from `/etc/ssl/certs`. TLS errors are not ignored.

The Pi 400 results of 2026-11-13 (`docs/image-loader.md`) show the effect:

| Source | Result |
| --- | --- |
| Public HTTPS JPEG (Unsplash, `w=640`) | loaded in 338 to 688 ms, 640x427 |
| Public plain HTTP JPEG | loaded in 68 to 161 ms |
| Mac-served HTTP image over USB Ethernet | loaded in 72 to 82 ms |
| HTTPS with a self-signed certificate | rejected, `SSL handshake failed: The certificate is self-signed, and untrusted` |
| Unresolvable host | rejected, `Host rnqnx-missing.invalid not found` |

## Device evidence and limits

- GIF and WebP animation play on the Pi 400. The PR 149 run 2 captures show the GIF chip cycling yellow, green and blue and the WebP chip changing between red and green (`docs/evidence/pr149-pi400-run2-2026-11-19/`). A growing `ExpoImage`, memory and disk clears, `loadAsync`, a blurhash and GIF start and stop ran on 2026-11-13 (`docs/evidence/expo-image-device-2026-11-13/`, `docs/validation/pr159-device-image-2026-11-13.md`). No frame rate, latency or memory figure accompanies any of them.
- The remote-image card in run 2 logged load times of 154149 ms and 618203 ms for a URL that loaded in under a second on 2026-11-13, and the key-hold run logged 30905 ms. The receipts record these numbers without an explanation. Treat network image loading in the November 19 runs as unexplained.
- The worker, cache-clear and SVG delivery changes have host evidence (loopback HTTP fixtures, Hermes tests, sanitizer builds), each with a control that fails on the original source. The receipt states that the current-delta QNX cross-build and a Pi run of the SVG image change were not run, and the image-loader document says the worker and cache-clear changes still need their own target receipt.
- Cancellation by request ID, cross-process caching and source-header props on React Native's own `Image` are not implemented.
